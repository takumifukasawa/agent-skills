# context-catchup — docs と memory から「現在地」を読み込む

> **どちらを使うか**: このスキルは**置き場が決まっていないリポジトリ**向けに、docs・assistant memory・VCS を横断して探す。`.harness/` と `docs/handoff.md` があるリポジトリ（agent-harness 導入済み）では `session-catchup` を使う。索引 → handoff → VCS の順が決まっているぶん安く済む。

セッションをまたぐと文脈は失われる。一方でプロジェクトには、過去の自分が残した docs・assistant memory・コミット履歴という**再構築用の素材**が既にある。このスキルは、それを**安く・順序立てて・実態と照合しながら**読み込み、次の一手を決められる形のブリーフィングにする。

素朴にやると 2 通りに転ぶ:
- **全部読む** → トークンを溶かし、しかも古い記述で頭が埋まる（新しい事実が古い事実に埋もれる）。
- **読まない / 断片だけ読む** → 「revert 済みの機能を実装済みと信じる」「終わった実験の続きを提案する」といった誤前提で走り出す。

避けたいのはこの 2 つなので、**索引から入り、resume point を特定し、最後に VCS の実態と突き合わせる**という順序を守る。

## いつ使うか / 使わないか

- 使う: 久しぶりの再開、別セッションからの引き継ぎ、初見のリポジトリで「何が進行中か」を掴みたい時、次に何をやるか決めたい時。
- 使わない: 単発の質問（「この関数何してる?」）、既にこのセッションで文脈を積んでいる時、特定ファイルの実装作業中。

## 出力の契約（先に目的地を決めておく）

最後に返すのは**ブリーフィング**であって、読んだファイルの要約リストではない。この形に収める:

1. **プロジェクトの構図** — 何を作っているか / 成功をどう測るか / 意思決定の単位（モジュール、リリース単位、実験アーム など、そのプロジェクトが「1 つの変更」と数えている粒度）。既に確定している「学習」があればそれも（例: 何を試して何が効かなかったか）。
2. **直近の状態** — 表形式で `項目 | 状態`。状態は *実装済み・測定前 / revert 済 / 未コミット / 未着手* のように**曖昧さのない語**で書く。
3. **次にやることの候補** — docs/memory に明示された resume point を、**依存順・順序制約つき**で。順序制約（「A を先にやらないと B で壊れる」）は最も価値が高いので必ず拾う。
4. **作業上のルール** — 指示ファイル(CLAUDE.md 等)と feedback 系 memory 由来の禁止事項・優先順位。タスクに直接関係なくても載せる（**行動の仕方を変える**情報なので）。
5. **不明点・矛盾** — docs の記述と実態がズレている箇所。ここが後で一番効く。

各項目に**出典パス**を添える。ファイル本文の長文引用はしない（ユーザーは元ファイルを開ける）。

## 手順

### 1. 素材の在り処を洗い出す（読まずに一覧だけ）

まず `ls -la`（mtime とサイズが出る）と指示ファイルのポインタで、**読む候補**を作る。この時点では中身を読まない。

| 素材の種類 | 何が取れるか | 探し方 |
|---|---|---|
| 指示ファイル | 規約・docs の置き場所・禁止事項 | リポジトリ root の `CLAUDE.md` / `AGENTS.md` / `README.md`、ユーザー global の指示 |
| プロジェクト docs | 設計・提案・既知の問題・引き継ぎ | 指示ファイルが指す場所。無ければ `docs/`, `**/Docs/`, `doc/`, `notes/` |
| assistant memory | 過去セッションの確定事項・ユーザーの好み | ハーネス依存。Claude Code なら `~/.claude/projects/<path-slug>/memory/`（`MEMORY.md` が索引）。セッション冒頭で索引が既に読み込まれていればそれを使う |
| VCS 状態 | 「実際に何が起きたか」の唯一の一次ソース | `git log --oneline`, `git status --short`, ブランチ名, 未 push コミット。VCS が無い環境ならファイルの mtime と docs だけで進め、手順 4 の照合が弱くなることを出力で断る |
| 成果物・データ | 実験/分析/ビルドの結論 | `analytics/`, `reports/`, `dist/`, CI 成果物など（プロジェクト依存） |

**mtime で並べる**のが効く。直近数日〜数週間に触られた doc が「今動いているスレッド」であることが多く、古い doc は背景知識として後回しでよい。

### 2. 索引レイヤーを並列で読む

最初に読むのは**索引・目次の役割を持つもの**。信号/トークン比が最も高い。

- memory の索引（`MEMORY.md` 等）→ そこから**関連する memory 本体**を選ぶ。全部は読まない。
- docs のうち索引・横断ドキュメント（バックログ、changelog / バージョン履歴、ロードマップ、既知の問題一覧）。
- **引き継ぎ / handoff / WIP と名の付く doc** — これは「次のセッションの自分に向けて」書かれているので最優先。

複数ファイルの読み込みは**1 メッセージにまとめて並列で**投げる。候補が数十本ある規模なら探索を sub-agent に fan-out して**結論だけ**返させてもよい（ユーザーが sub-agent 利用を許容している場合）。

### 3. resume point を特定する

「次に何をするか」は、たいてい以下のどれかに明示的に書かれている。探して拾う:

- handoff doc の「次にやる」「未実装」「実装順序」節。
- memory の `現在地 / resume point / 残タスク` 節。
- バックログの `🚧 進行中` 相当の項目。
- **ブランチ名**（作業中の feature / version を示す）。
- **未 push コミット** — 「済んでいるが世に出ていない」もの。
- **未コミットの作業ツリー** — 「今まさに手が動いていた」もの。ここが最も新しい情報。

### 4. 実態と照合する（このスキルの核心）

docs と memory は**書かれた時点のスナップショット**で、コードは動いている。報告前に、これから行動が依存する主張だけを現物で確認する。

- **「実装済み」と書いてあっても信じない** → `git log --oneline` で **revert コミットの有無**を確認する。ドキュメントは実装時に書かれ、revert 時に更新されないことが多い。対象ファイル/シンボルがまだ存在するかも見る。
- **「未着手 / 未ビルド」と書いてあっても信じない** → `git status` と主要な設定ファイルの diff を見る。作業ツリーが doc より先に進んでいることがある。
- **「現在有効な設定」は必ず一次ソース（コード・設定ファイル）で確認**する（フラグ、エントリポイント、依存バージョン、有効な実験アーム 等、プロジェクトの意思決定単位にあたるもの）。doc の表は古くなる代表格。
- **`file:line` の検証は、そこを触る時だけ**やる。全部を verify するとコストが手順の意味を失わせる。「行動が依存する主張だけ検証」が原則。
- 矛盾を見つけたら**黙って直さず**、出力 5 に「doc はこう書いてあるが実態はこう」と並べて報告する。どちらが正かはユーザーが決める。

### 5. ブリーフィングを返して、止まる

上の「出力の契約」の形で返し、**最後に「どれから進めるか」を聞いて止まる**。これは読み込みのスキルであって実装のスキルではない。良さそうな次の一手が見えても、勝手に着手しない（ユーザーの優先順位を知らないまま動くのが一番損）。

同様に、古くなった memory / doc を見つけても**このスキルの中では書き換えない**。指摘に留め、更新はユーザーの指示で別途行う。

## やらないこと

- docs ディレクトリを頭から全部読む（コスト・ノイズとも最悪）。
- memory の記述を無検証で事実として断言する。
- 「理解しました」だけで終える／読んだファイル名の羅列で終える — **状態と次の一手**を言えて初めて価値が出る。
- 読み込みの流れでそのまま実装・修正を始める。
- 見つけた矛盾を勝手に「修正」する（doc の書き換えを含む）。

## Worked example: ハイパーカジュアルゲーム (Unity, AB テスト運用)

※ 以下は具体プロジェクトの実例。**手順の当てはめ方**として読み、自分のプロジェクトの構造に置き換えること。

**素材**: `CLAUDE.md` が `Assets/Docs/` と `Assets/Kayac/MatchingSystem/Docs/` を指定 → その 2 つを `ls -la`。assistant memory は `~/.claude/projects/<slug>/memory/`（17 本、索引 `MEMORY.md` あり）。VCS は feature ブランチ + 未 push コミット 20 本。

**読んだ順**: memory 索引（既に context にあった）→ 索引から関連 4 本を並列 Read（進行中の設計 / 次の戦略 / 後方互換の feedback / 分析基盤）→ docs から `Handoff_*.md`(引き継ぎ) `VersionHistory.md`(版履歴) `FeatureBacklog.md`(バックログ) `KnownIssue_*.md` → `git log/status/diff`。全 50 本の docs のうち読んだのは 4 本。

**照合で出た 3 つのズレ**（doc だけ / memory だけ を見ていたら全部間違えていた）:

1. memory に「online レベル分離の設計を実装」とあり、コミット履歴にも `feat: ...` があった。しかし `git log --oneline` に**その直後の `Revert "feat: ..."` があった** → 実態は「revert 済み・未実装」。**なぜ罠か**: feat コミットの存在は実装の証拠にならない。ドキュメントと memory は実装時に更新され、revert 時に更新されていなかった。
2. 版履歴 doc に「vN は未ビルド」とあったが、作業ツリーで `buildVersion.txt` が `421 → 430` に変わっていた（未コミット）→ 実態は「ビルド準備が進行中」。**なぜ罠か**: doc は前日に書かれ、その後の手作業が反映されていない。**未コミットの作業ツリーが最新の事実**。
3. 実験アームの一覧が doc・設定ファイル・作業ツリーで三者三様に見えた（1 アセットが `Resources/` から削除され `ResourcesTmp/` に未コミットで移動していた）→ アーム削除が進行中。**なぜ罠か**: 「現在の live 構成」は doc でなく一次ソース（この例では AB テスト定義のコード + `Resources/` の実ファイル）で確認する必要がある。

**出力**: 構図（KPI = プレイ時間 × 広告密度 / 過去実験は構造的に null という確定学習）→ 状態表（実装済み・測定前 / revert 済 / 未コミット）→ 次の候補 3 つ（**順序制約つき**: 共有カタログの割当を先にやらないと後段でオンラインが壊れる）→ 作業ルール（後方互換最優先 / 課金クエリは明示 GO 待ち / 型は `var`）→ 最後に「どれから進めますか」。

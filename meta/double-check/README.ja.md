# double-check

計画や実装が本当に正しいかを、エージェント自身の要約を信じずに、コード・ファイル・仕様といった一次ソースから自分で導き直して確かめる（検算する）メタスキルです。

> このファイルは人間向けの説明です。Claude が実際に読むのは [SKILL.md](./SKILL.md)（英語）で、動作はそちらで決まります。

## こんなときに使う
- 「検算して」「ダブルチェックして」
- 「この計画を見直して」
- 「本当にこれで合ってる？」
- 「cross-check this plan/implementation」

明示的に頼まれたときだけ動きます。自動では発火しません。

組み込みの `/code-review`（diff のバグ探し）や `/verify`（アプリを動かす）とは役割が違い、**推論が成り立っているか、意図と合っているか**を確かめます。確認する対象は「反証すべき主張」として、疑ってかかります。

## 2 つのモード
- **A: 計画チェック（実装前）**
  - 前提: 計画が想定しているファイル・関数・API・型が実在し、想定どおりに動くかを実物を読んで確認します
  - 要件カバレッジ: ユーザーの依頼を項目に分け、それぞれを計画のステップに対応づけ、漏れを指摘します
  - 矛盾と順序: 内部の矛盾、足りない前提、順番の誤り
  - 見落とした代替案とリスク: もっと簡単で正しいやり方はないか、何が壊れうるか
- **B: 実装チェック（実装後。auto モードの後によく使う）**
  - 「何をしたか」の要約ではなく、実際に変更されたファイルを読みます
  - 要件や計画の各ステップが、コードのどこで満たされているかを対応づけます
  - エッジケース、エラー処理、周辺を壊していないかを確認します
  - 食い違いがあれば具体的な修正を提案し、auto モードが間違ったものを書いた場合は revert するか patch するかをはっきり示します

## やること
1. 対象（計画か、diff か、両方か）と、その裏にある意図・要件を 1〜2 行で言い直します。不明なら確認します。
2. 関係するファイル・コード・仕様を読み、計画や実装と比べる前に自分で結論を出します。
3. 項目ごとに ✅ 確認済み / ⚠️ 不確か / ❌ 誤り の判定を付け、根拠（`file:line`）と理由を添えます。
4. ❌ / ⚠️ には、具体的な修正か、次に必要な確認を示します。
5. 最後に「このまま進めてよい」か「修正が必要」かを判断し、主なリスクを 1〜3 個挙げます。

## 注意点
- 計画を読み直してうなずくだけなのは失敗です。要点は一次ソースから**独立に導き直す**ことです。
- ソースで確かめられない主張は「unverified」とし、確認済み扱いにしません。
- 徹底しているように見せるために問題をでっち上げません。問題なしも正当な結果ですが、そう言える根拠は示します。

# context-handoff — 次のセッションのために docs と memory を最新化する

セッションをまたぐと文脈は失われる。[context-catchup](../context-catchup/SKILL.md) はそれを**読む側**から解決するが、読む素材が古い・矛盾している・そもそもコミットされていないなら、どれだけ上手に読んでも誤った現在地に着地する。このスキルは**書く側**、つまりセッションを畳む前に素材そのものを信頼できる状態に直す。

原則: **「次のセッションが context-catchup したとき、検証してもズレが出ない状態」を目的地にする。** catchup が読むもの（索引 → resume point → VCS 照合）を、そのまま書く側のチェックリストとして使う。

## いつ使うか / 使わないか

- 使う: セッションを立ち上げ直す前、長い作業の区切り、別マシン・別セッションへ引き継ぐ前、/clear の前。
- 使わない: 作業がまだ途中で数分後に続ける時（コスト倒れ）、単発の Q&A しかしていないセッション（更新する事実がない）。

## 手順

### 1. 棚卸し（読まずに一覧から）

並列で取る:

- `git log --oneline` + `git status --short` — 特に**未追跡ファイルの中に doc がないか**を見る。セッション（あるいは並行する別セッション）が書いた「正史」ドキュメントが未コミットのまま残っているのが、引き継ぎで最も失われやすい資産。
- assistant memory ディレクトリの `ls -la`（Claude Code なら `~/.claude/projects/<path-slug>/memory/`、索引は `MEMORY.md`）— **mtime を見る**。自分の把握より新しい mtime のファイルは、並行セッションが更新した可能性がある。
- docs ディレクトリの一覧（指示ファイルが指す場所）。

### 2. 三層整合チェック（このスキルの核心）

memory は多くの構造で**三層**に分かれており、それぞれ独立に更新される — だからバラバラに古くなる:

1. **索引の一行**（`MEMORY.md` の行）— 毎セッション context に載る層
2. **memory ファイルの `description` フィールド** — 想起の判断に使われる層
3. **memory ファイルの本文** — 実際に読まれる層

別セッションが本文と description だけ直して索引を忘れる、逆に索引だけ直る、といった食い違いが実際に起きる。**三層すべてを最新の事実（VCS・現物ファイル）と突き合わせ、負けている層を勝っている層に揃える。** どの層が正か迷ったら mtime と VCS が審判。

あわせて **"as of <日付>" の化石化**を探す。「現在のフェーズ」を名乗る memory / doc の日付が数フェーズ前を指しているのは、次セッションを最も確実に誤導するパターン。

### 3. 並行更新に敬意を払う

書き換える前に**必ず読み直す**。別セッションが既に更新済みなら、自分の書きかけよりそちらが新しく・正しいことがある — その場合は**触らず勝ちを認める**のが正解で、上書きは後退になる。Write が「file modified since read」で弾かれたら、それは警告であってリトライ対象ではない。

### 4. 未コミットの正史 doc を救出する

未追跡 / 未コミットの docs があれば、**プロジェクトのコミット制約**（秘密情報・個人データ・そのプロジェクト固有の禁止事項、コミットメッセージ規約）を確認したうえでコミットする。doc はコミットされて初めて「次セッションが git から辿れる事実」になる。逆に、**意図的に未追跡のもの**（そのプロジェクトが追跡しないと決めているディレクトリ等）はそのままにし、報告で「意図的」と明言する。

### 5. このセッションの事実を書き足す

memory / handoff doc に足すのは、**コードと git から導出できないもの**だけ:

- 決定とその理由（採用案だけでなく、落選案と落選理由 — 再浮上した時に効く）
- 実機・実環境で踏んだ罠と直し方（「再発したらまず X を見る」の形にする）
- **明示的な resume point**（`NEXT: ...`）と**順序制約**（「A が先、でないと B の原因が切り分けられない」）
- 相対日付は絶対日付に直す

書かないもの: セッションの時系列ナラティブ、git log が既に語ること、コードを読めば分かる構造。

### 6. 触らない判断も成果物

古い doc がすべて更新対象ではない。**初期計画・歴史記録として役割を終えた doc** は、現状の正がどこにあるか（例: 「現状は docs/05 に集約」）さえ明確なら書き換えない。むしろ全面改稿は履歴を壊す。報告で「確認したが意図的に触らなかったもの」を挙げること — 次のセッション（や未来の自分）が同じ確認を繰り返さずに済む。

### 7. 報告して終える

最後の報告は「更新しました」ではなく、**次のセッションが何を見つけるか**の形で:

1. 更新したもの（何がどう古かったか一言ずつ）
2. コミットしたもの
3. 確認して触らなかったもの + その理由
4. **次セッションの再開地点** — 「memory を読めば『X 待ち』『Y は Z から』という状態から始められる」と言い切れること

これが言い切れないなら手順のどこかが漏れている。

## やらないこと

- 三層のうち 1 層だけ直して満足する（食い違いを増やすだけ）。
- 読み直さずに memory を上書きする（並行セッションの更新を潰す）。
- 歴史 doc の全面リライト。
- git が既に記録していることの memory への複写。
- コミット制約（秘密・個人データ・プロジェクト固有の禁止事項）を確認せずに未追跡ファイルをコミットする。

## Worked example: 生成映像 VJ システム (Python + Unity, 複数セッション並行)

※ 具体プロジェクトの実例。**手順の当てはめ方**として読み、自分のプロジェクトの構造に置き換えること。

ユーザー: 「一回セッション立ち上げ直したいから、docsとかメモリとか確認して最新版にしてほしい」。

**棚卸しで出たもの**: `git status` に未追跡の `docs/10_<新機能仕様>.md`（別セッションが書いた確定仕様書、未コミット）。memory ディレクトリの mtime で、ある memory が自分の把握（このセッションの要約時点）より**後**に更新されていた — 並行セッションの痕跡。

**三層チェックで出た食い違い 2 件**:

1. 新機能の memory — `description` は「仕様確定・モデル決定済み」に更新済みなのに、**索引 `MEMORY.md` の行は「仕様検討中・別ルートが有力」のまま**。索引だけ読む次セッションは、確定済みの検討を再演するところだった。→ 索引行を description に揃えた。
2. 「現在のフェーズ」memory — 本文は最新の実装まで記録済みなのに、**`description` が 3 フェーズ前の "as of <古い日付>"** のまま（「これから作る」と書かれた機能は完成済みだった）。→ description を書き直し、本文にこのセッションの 2 事実（シーン側設定の直し方 = 「再発したら report の mask=% を見る」、並行仕様トラックの存在と順序制約 = 「実機テストが先、でないと原因が切り分けられない」）を追記。

**並行更新への敬意**: 新機能 memory の本文を書き直そうとしたら Write が「file modified since read」で弾かれた。読み直すと**別セッションが既に自分の書きかけより良い内容に更新済み**（落選ルートの理由・プロセス上の教訓まで記録されていた）— 触らず勝ちを認めた。

**救出と不干渉**: 未追跡の仕様書は、プロジェクトのコミット制約（個人写真・パスをコミットしない）を確認してからコミット。一方、初期計画 doc が旧世代の構成名のままなのは**触らない**と判断（現状の正は別 doc に集約される構造で、初期計画は歴史記録）。Unity プロジェクト一式が未追跡なのも**意図的**（ユーザーが自分で管理）なのでそのまま。

**報告**: 更新 3 点 + コミット 1 点 + 触らなかった 3 点（理由つき）+ 「次のセッションは『実機テスト待ち（設定は修正済み、Play し直すだけ）』『新機能は仕様書の Editor 実測から』という状態から始められる」で締めた。

# blog-review

Markdown で書かれたブログ記事を、内容・日本語・公開フォーマットの 3 つの観点でレビューするスキルです。「直す → また見てもらう」の往復を前提にしていて、再レビューでは差分だけを返します。

> このファイルは人間向けの説明です。Claude が実際に読むのは [SKILL.md](./SKILL.md) で、動作はそちらで決まります。

## こんなときに使う
- 「ブログをレビューして」「記事を推敲して」
- 「この md 記事を見て」
- `/blog-review <path.md>`
- 直した版をもう一度見てほしいとき

## やること
1. **対象を受け取る** — Markdown ファイルのパスを引数で受け取る。無ければどの md かを確認し、複数なら 1 記事ずつ見る
2. **3 つの観点でレビューする**
   - **内容（C）**: 構成と論理、読者目線のわかりやすさ、技術的な正確さ、タイトル・導入・SEO
   - **日本語（J）**: 誤字脱字・誤変換、表記ゆれ・文体の混在、冗長さや長すぎる文などの読みやすさ（提案ベースで著者の文体は尊重）
   - **公開フォーマット（F）**: 見出し階層（本文は `##` から）、目次、front matter、脚注・引用・リンク、画像の alt、コードブロックの言語指定
3. **指摘を出す** — 観点ごとに ID（C1, J1, F1…）と優先度（高・中・低）を付け、箇所は見出し名か原文の引用で示す。最後に総評と優先対応トップ 3
4. **修正を適用する** — 承認を得たら、機械的な校正レベルの修正（J）だけを md に直接反映し、反映した指摘を一覧で返す。内容や文体（C など）は提案にとどめる
5. **再レビュー** — 直した版で呼ばれたら、git 管理なら `git diff` で変更箇所に注目し、前回の各指摘を ✅解決 / ⚠️未対応 / 🔁部分対応 で判定、新しく混入した誤字や流れの崩れを拾い、差分だけを返す

## 注意点
- 特定のブログサービスには依存しない。はてな / Zenn / Qiita / note などのサービス名をユーザーが挙げたときだけ、その作法を加味する。不確かな記法は断定せず「サービスの仕様を確認」と添える
- 技術的な主張は「要検証」が基本で、確証があるものだけ誤りとする（CG / WebGL / シェーダなどは特に）
- 推測の修正は「自信度: 低」と明示する
- 好みを押し付けず、指摘には必ず理由を添える
- 一度に大量に出さず、優先度の高いものから。低優先は件数だけでもよい

# version-history-update — 版シグナル源から変更履歴を更新する

「各版で何をやって、結果どうだったか」を1つの changelog ドキュメントに保つ。情報は普段コードやアセット・分析結果に散っているので、**それらの一次ソースから再抽出**し、既存 doc を壊さずに**差分マージ**する。フル再生成ではない（人手で整えた記述を潰さないため）。

## いつ使うか
- 新しい版を出した/実験を締めた後、履歴 doc に反映したいとき。
- 履歴 doc がまだ無く、散在情報から初版を組みたいとき（初回はフル生成、以降は差分マージ）。

## 手順

### 1. 履歴 doc と版シグナル源を特定する（プロジェクト依存＝毎回探す）
まず「更新対象の履歴 doc」を探す（例: `**/VersionHistory.md`, `**/CHANGELOG.md`, docs 配下）。無ければ新規作成する場所をユーザーに確認。

次に、このリポジトリの**版シグナル源**を洗い出す。以下は探すべき「種類」— 実ファイルはプロジェクトごとに違うので grep/探索で特定すること:

| シグナル源の種類 | 何が取れるか | 探し方の例 |
|---|---|---|
| 実験/AB テスト定義 | アームの追加/削除/復活の履歴、現行 live アーム、ビルド別分岐 | テスト設定ファイル/リモート設定 (テスト名一覧 + アーム増減が追える履歴・コメント)。"drop/落とした/removed", "test", "variant", "abtest" 等で grep |
| 設定 variant の記述 | 各 variant が「何を変えた版か」(親 + 変更点) | 設定アセット/ファイルの memo/description/note フィールドを一括抽出 |
| 分析の結論 | 各実験の結果 (勝ち/null/負け/ドロップ) と根拠 | 分析結果の doc / 実験メタデータの結論欄 / レポート |
| 配信ロールアウト表 | 版 → 配信日時 | リリース/配信管理の doc・表 (リリースノート, 配信スケジュール 等) |
| VCS release コミット | 版の時系列アンカー | `git log --oneline` をリリース系パターン ("build"/"release"/tag/バージョン番号) で絞る |
| 既存メモ/ノート | 過去の確定事項・経緯 | プロジェクトのメモ、assistant memory |

大量にある場合（variant が数十個等）は、複数の探索を並行に投げて素材を集めると速い。

### 2. 差分を特定する
- 既存 doc を読み、**すでに記録済みの最新版**を把握する。
- シグナル源から、それより新しい版 / 内容が変わった版だけを抽出する（全部を作り直さない）。

### 3. 非破壊マージ（核心）
- **スキャン用タイムライン表**に新しい行を足す（版 → 配信日 → 見出しの変更 → 結果）。
- 新版の**詳細セクション**を足す（導入 / 結果 / 出典）。結果が未確定なら `WIP / 測定前` と明示（後で埋める）。
- 「**現在の live 状態**」(有効フラグ/現行アーム等) のセクションを最新に更新する。
- **古い版の記述・人手で整えた散文は残す**。フル再生成で上書きしない。
- **各主張に出典パスを併記**する（`file:line` か doc パス）。乖離時にどれを正とするか（例: コミット日付が壊れている版はロールアウト表を正）を注記。
- 抽出中に見つけた**データ不整合/罠**は "Notes / 既知の罠" に記録する（命名ミスマッチ、アーカイブと live の区別、複製ファイル 等）。これが後で最も効く。

### 4. 検証（doc なのでテストでなく整合確認）
- タイムライン表の「版↔配信日」をロールアウト表と、「アーム増減」をテスト定義のコメントと突き合わせて一致確認。
- variant 記述をいくつか実ファイルと照合。
- 「現在の live アーム/フラグ」がテスト定義の現行値と一致するか再確認。
- 履歴 doc へのリンクを索引 doc (バックログ/README 等) に足し、リンク切れが無いこと。

## 推奨する doc 構成（既存があればそれに合わせる）
1. スキャン用タイムライン表（1版1行）
2. 近年 era の詳細（結果が記録されている版を厚く）
3. 実験軸のサマリ（版跨ぎで動いている AB 軸の結論）
4. 旧 era の系譜（variant memo 由来の親子ツリー、簡潔に）
5. 付録: 全 variant 表
6. Notes / 既知の罠

## やらないこと
- コード/アセットの変更（履歴 doc の記述のみ）。
- 結果が出ていない版に憶測の結論を書く（`WIP` にする）。
- フル再生成で人手の記述を潰す。

## Worked example: ハイパーカジュアル (archery king online)
※ 具体パスはこのプロジェクト固有。**手順の当てはめ方の例**として読み、自分のプロジェクトのパスに置き換えること。

- **履歴 doc**: `Assets/Docs/VersionHistory.md`（索引は `Assets/Docs/FeatureBacklog.md` からリンク）。
- **版シグナル源**:
  - 実験定義 = `Assets/Art/Scripts/AbTests.cs`（`Test` enum + `SettingTable` 配列 + 「vX で Y を落とした/復活した」コメント履歴 + `#if UNITY_LUNA` のビルド別分岐で production/Luna のアームが違う）。
  - variant 記述 = `Assets/Resources/VersusSettings/*.asset`(live) と `Assets/ResourcesTmp/VersusSettings/*.asset`(アーカイブ=実行時ロードされない) の **`memoTextArea`** フィールドを一括抽出（`memo:` 行を grep）。live/archive はディレクトリで判定。
  - 分析結論 = `analytics/analyses/*/meta.json` の `title`/`notes`（例 v40B=★負け, v41=上乗せ無し, v42=全null）。
  - ロールアウト表 = `analytics/reference/README.md`（版→25%/66% 配信日時）。
  - 時系列アンカー = `git log` の `build vN` コミット。
- **この例で出た「罠」(Notes に記録した実例と、なぜ罠か)**:
  - あるアーム(`VersusSetting_v43A`)の `GameVersion` 文字列が **`042A`** でファイル名 `v43A` と不一致だった。**なぜ罠か**: 分析側で「GameVersion」列をキーに名寄せすると v42A と衝突して集計が混ざる（AB の group1 値 `SettingTable_v43A` は別なので AB 集計自体は無事、という切り分けも記録する価値がある）。単に「不一致がある」ではなく、どの結合で事故るかまで書く。
  - `_DEBUG`/`_tmp`/`_Playable` サフィックスは正規 variant の複製（親を正とし注記扱い）。`ResourcesTmp/` は非ロードのアーカイブ。コミット日付が壊れた版はロールアウト表を正とする。
- **構成**: タイムライン表 / 近年詳細(v36〜v43) / AB軸サマリ(InterstitialInterval・Vibration 等) / 旧era系譜(v1〜v35) / 全 variant 付録 / Notes。
